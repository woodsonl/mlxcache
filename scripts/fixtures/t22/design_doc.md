## Problem Statement

Apple Silicon Macs (M5 Ultra Mac Studio: up to 512GB unified memory) are becoming serious local inference engines, but there is no KV cache management layer for MLX/macOS. LMCache (11.9k stars, PyTorch Foundation) does this for vLLM/CUDA only. Every MLX serving process re-prefills expensive shared context — system prompts, repo context, agent histories — because KV state dies with the process. The project: an MLX version of LMCache, as a daemon sitting between coding agents (or any OpenAI-compatible client) and local/network LLM engines.

## What Makes This Cool

- One Mac Studio becomes a shared inference brain: prefill once, every session, every app, every process reuses it. Warm start for a 100K-token repo context in seconds instead of minutes.
- Unified memory removes the wall LMCache exists to fight: no GPU→CPU shuttle, no RDMA. KV persistence avoids a memory-hierarchy shuttle, but it is not free: a 50K-token checkpoint for a mid-size model is plausibly 1-5 GB (bytes/token must be measured — see R1-5 measurement gate below). The daemon's job is still dramatically simpler than LMCache's tiering — policy and persistence, no inter-process tensor shuttling — with the same hit-rate wins.
- Suspend/resume: a 200K-token agent session survives daemon and process restarts.
- The founder is also building a ds4-alternative engine — the daemon's cache contract is designed so their engine is the first-class adapter.

## Constraints

- KV tensors are engine-private (layout, dtype, attention variant). Cross-engine KV sharing is impossible; the contract must be engine-agnostic at the blob/policy level only.
- Cross-machine KV transfer is out of scope for v1 (gigabytes over a network; LMCache needed RDMA for a reason). Multi-Mac arrives later via routing, not KV transfer.
- Solo builder, AI-heavy workflow. Ship value in weeks, not months.
- A sibling product shares the policy DNA: this repo owns the MLX/macOS deep integration (KV persistence, suspend/resume, engine adapters); the sibling owns the universal cross-platform proxy layer.

## Approaches Considered

### Approach A: Token-Prefix Proxy (minimal viable)
Pure HTTP proxy; hashes token prefixes, routes to the backend holding the longest match, applies ds4-style policy (protect extendable anchors, auto-warm). No KV access in v1. Effort S (weeks), Risk Low. Works with any OpenAI-compatible backend day one; hit-rate ceiling ~60-80% (each engine process still re-prefills what only it has seen). Auto-warm mechanism: issue a prefill-only request so the engine caches the prefix without generating tokens — locally this is `max_tokens: 0`, **which must be verified against mlx-lm's server (folded into the Next Steps #3 benchmark); if rejected, fallback is `max_tokens: 1` + discard the output**; cloud backends generally require max_tokens ≥ 1, so warming is backend-specific policy in the proxy layer. → Evolved into a sibling repo.

### Approach B: Cache Contract + Engine Adapter (recommended for this repo)
Approach A plus a formal engine-agnostic cache contract: the daemon indexes token prefixes; engines push/pull serialized KV checkpoints (safetensors blobs keyed by prefix hash) through a small adapter API. Disk tier for suspend/resume included. Founder's engine first-class; mlx-lm adapter second. Effort L, Risk Medium.

### Approach C: Engine-Native Cache
Skip the daemon; build the cache contract into the founder's own engine (OpenAI-compatible API with cache-control endpoints, multi-process cache store via memory-map or XPC). Effort M, Risk Medium. Deferred: orphans the existing MLX community until the engine ships; universality (the 10x vision) delayed.

### Contract rules resolved by review (binding, go into the contract spec)

- **Mismatch behavior (R1-1):** on any fingerprint/tokenizer/dtype mismatch, the checkpoint is treated as a miss and the request falls through to normal prefill. Never serve incompatible KV. Mismatched blobs are quarantined, not deleted, for diagnostics.
- **Tokenization ownership (R1-2):** the engine's adapter tokenizes and reports token IDs (it already has the tokenizer); the daemon keys checkpoints by the adapter-reported token-ID prefix and pins the tokenizer artifact hash in checkpoint metadata. The daemon never re-tokenizes.
- **Concurrency (R1-3, refined R2-1):** single-flight on identical uncached prefixes — a concurrent request for the same prefix blocks on the in-flight prefill and is served from its result (one behavior, no either/or); checkpoint blob push/pull is serialized per-blob with an atomic publish (write-temp-then-rename).
- **Restart with in-flight requests (R1-4):** streaming connections drop on daemon restart; clients retry (standard HTTP semantics). Persisted checkpoints survive; in-flight generation state does not.

### Measurement gate before the disk tier is designed (R1-5)

Before committing to checkpoint persistence: measure bytes/token for one representative model (e.g. Qwen3-32B-4bit), measured serialize + deserialize wall time on the target disk, and derive whether the 2s TTFT resume budget holds. If the round-trip fails the budget, v1 ships memory-resident only and the disk tier waits for compression (fp8/quantized KV, CacheGen-style) — the suspend/resume criterion defers with it.

**R1-5 MEASURED (2026-09-25, mlx-lm 0.31.3, Apple Silicon):**

*Qwen2-0.5B-Instruct (24 layers):*
- bytes/token: **12,288** (12 KB/token; 8K tokens = 98 MB)
- serialize: **20 ms**; deserialize: **<1 ms** (memory-mapped safetensors) at 8K tokens; prefill 697 ms

*Qwen2.5-7B-Instruct-4bit (28 layers, 4-bit):*
- bytes/token: **57,344** (57 KB/token; 8K tokens = 459 MB → 50K tokens ≈ 2.9 GB, in the design's 1-5 GB envelope for a mid-size model)
- serialize: **526 ms**; deserialize: **<1 ms** at 8K tokens; prefill **10.2 s**

*Qwen3-32B-4bit (the named representative, 64 layers):*
- bytes/token: **262,150** (262 KB/token; 8K tokens = 2.1 GB → 50K tokens ≈ 13 GB, above the 1-5 GB envelope — see caveat)
- serialize: **203 ms**; deserialize: **1 ms** at 2K tokens; prefill **11.1 s**

- **2s TTFT resume budget: HOLDS with margin at all three sizes** — deserialize is negligible (memory-mapped); the dominant resume cost is delta prefill compute, not I/O. A hit eliminates the 10-11s prefill.
- **Thesis guard PASSED at all three sizes:** generation resumed from a saved-then-loaded prompt cache is token-for-token identical to scratch. Additionally the real **adapter path** (`MlxLmEngine.prefill` → persisted blob → `generate_from_blob`, what the daemon actually calls) is token-identical to scratch, verifying the cache-convention fix (`test_adapter_prefill_resume_matches_scratch`). Disk tier viable; suspend/resume NOT deferred.
- **Real daemon end-to-end verified** (7B-4bit): request 1 miss → checkpoint persisted (957 KB, 56 safetensors tensors = 28 layers × K,V) → request 2 hit reuses it. No errors.
- Caveat: byte/token scales with layer count × hidden size. At 32B-4bit, a 50K-token prefix is ~13 GB, beyond the 1-5 GB envelope the design assumed for a mid-size model; long-context 32B persistence needs the compression tier (fp8/quantized KV) rather than raw f16 KV. Identity + sub-ms deserialize hold structurally at every size.

**Quantized-KV probe MEASURED (2026-10-03, mlx-lm 0.31.3 / mlx 0.32.2, Qwen2-0.5B-Instruct, Metal; `sidecar/probes/quantized_kv_probe.py`):**

| config | bytes/token | 50K-token blob | greedy parity vs f16 (32 tokens) |
|---|---|---|---|
| f16 KV | 12,288 | 0.61 GB | baseline |
| 8-bit, group 64 | 6,529 (−47%) | 0.33 GB | **IDENTICAL 32/32** |
| 4-bit, group 64 | 3,457 (−72%) | 0.17 GB | diverges at token 0 (32/32 differ) |
| 4-bit, group 32 | 3,457 (−72%) | 0.17 GB | diverges at token 2 (30/32 differ) |

- **8-bit quantized KV is parity-safe AND persistence-safe**: `QuantizedKVCache.to_quantized(group_size=64, bits=8)` then `save_prompt_cache`/`load_prompt_cache` round-trips, and greedy generation from the reloaded quantized cache is token-for-token identical to the f16 run. 4-bit does NOT preserve greedy parity on this model — it is a sampled-decoding-only option, not a drop-in tier.
- **Resume budget at 8-bit (18,191-token prefix): load 0.6 ms + delta prefill 75 ms — the 2s budget holds with 25x margin.** The compression tier the caveat calls for is viable at 8-bit today; adopt by adding `bits=8, group=64` to the checkpoint fingerprint so f16 and q8 blobs can never cross-serve.

**7B resume budget MEASURED (2026-10-03, `sidecar/probes/resume_budget_probe.py`, mlx-community/Qwen2.5-7B-Instruct-4bit, Metal, 48 GB):** the step-2 open question is closed — wall-to-first-token after loading a persisted checkpoint at 7B is dominated by the single-token decode step, NOT by blob page-in. `load_prompt_cache` is mmap-lazy and the first forward pass touches state lazily, so TTFT stays ~2 orders of magnitude inside the 2s budget at every length measured, in both tiers:

| prefix | tier | blob size | load (ms) | TTFT (ms) | budget | first-token parity | full-stream parity |
|---|---|---|---|---|---|---|---|
| 27,281 | f16 | 1.56 GB | 0.4 / 1.0 | 80 / 145 | ✅ 25x margin | ✅ | ✅ (8 tok) |
| 27,281 | q8 g64 | 0.83 GB (−47%) | 0.7 / 1.5 | 59 / 111 | ✅ | ✅ | ✅ |
| 45,461 | f16 | 2.61 GB | 0.3 / 2.5 | 160 / 157 | ✅ 12x margin | ✅ | ✅ |
| 45,461 | q8 g64 | 1.39 GB (−47%) | 11.2 / 6.5 | 87 / 122 | ✅ | ✅ | ✅ |

- Second column pair = cold-ish load (2s idle gap) vs first load. Bytes/token: f16 = 57,343, q8 = 30,464 (−47%, exactly the T12 ratio — KV quantization cost is layer-count-proportional, not prompt-dependent).
- Prefill is the price: 51.8s (27K) / 110.5s (45K) one-time f16 publish (~520 tok/s at 7B on this GPU), which is exactly what the cache exists to amortize: a resumed session skips ALL of it.
- Parity at 7B: the persisted q8 stream matches the f16 in-memory reference token-for-token at both lengths, and every resume's first token matches — the q8 tier is parity-safe at 7B, not just at 0.5B.
- `load_prompt_cache` itself: 0.3–2.5 ms (f16) / 6.5–11.2 ms (q8) — the mmap-lazy load does NOT page in 1.5–2.6 GB eagerly; the probe's earlier 0.6 ms number was real, not an artifact. The daemon's load path can stay synchronous in the TTFT budget.
- Capability probe (`sidecar/probes/mlx_capability_probe.py`): prefill 9,908 tok/s (f16, 471 tokens), f16 KV round trip 12,305 bytes/token, `mx.compile` cannot wrap a model call that takes an MLX cache object (T14's FFI path must beat 9.9k tok/s eager, not a compiled number), tokenizer.encode ≈ 181 µs per ~930-char chat payload (T13 native-tokenize baseline).
- Lean greedy decode (T21, `sidecar/probes/lean_decode_ab.py`, opt-in via `MLXCACHE_LEAN_DECODE=1`): a daemon-owned argmax loop that skips stream_generate's per-token logsumexp, GenerationResponse accounting, and generator nesting is **token- and text-identical** to the stock path, but only **1.01x faster** — decode is GPU-memory-bound (~3.8 ms/token at 0.5B), so Python-side per-token cost is not a TPOT lever on this hardware. Kept default-off: it preserves exact protocol parity (yields EOS as the final frame, same 256-token implicit cap) and serves as the structure T14's native forward pass would slot into; the TPOT levers that remain are GPU-side (speculative decode, batching), not Python-side.

**Eviction reaper WIRED (2026-10-03, T-eviction):** the tested-but-dead `policy::eviction_score`/`EvictionCandidate` policy is now live in the daemon. `IndexEntry` gained a monotonic `last_used` (atomic touch on every lookup, through the read lock), the index exposes `eviction_candidates()` (with structural anchors: any prefix that a longer published checkpoint extends) and `remove_published()` (verify blob name + generation, remove, prune-free — tree nodes stay, entries go). `Orchestrator::evict_cold(persistence, max_entries, anchor_window)` applies the policy: anchors (recently served within window OR live chain bases) score 0 and are never reaped; the rest evict highest-score-first (`score = token_count` — biggest blobs free the most bytes per unlink). `AppState::evict_pass` is the single path used by both the background reaper and tests, so the `evictions` counter in /stats cannot drift from what was actually removed. Blob files are unlinked only after the index removal wins its verify race; a failed unlink is reconciled by the next startup rebuild (never resurrected mid-run). Env knobs: `MLXCACHE_EVICT_INTERVAL_S` (default 60, 0=off), `MLXCACHE_EVICT_MAX_ENTRIES` (default 0 = unlimited, historical behavior), `MLXCACHE_EVICT_ANCHOR_WINDOW_S` (default 900). Tests: 4 index-level, 4 orchestrator-level (chain-base protection, highest-score-first ordering, recency window, unlink agreement), 1 e2e (publish → reap → unlink → /stats → clean miss). Default remains unbounded — eviction is opt-in until the launch config decides the cap.

**Trace capture + replay harness LANDED (2026-10-03, step 5):** `MLXCACHE_TRACE=<path>` turns on one-JSONL-record-per-request capture (`crates/mlxcache-daemon/src/trace.rs`): bounded channel (4096) + dedicated writer thread; a record never blocks the request path (try-send, degrade-and-count — lost records surface on drop as a warning, meaning any derived score is a lower bound); the file truncates per session and per-record flush means a crash cannot lose the tail; an invalid path is a loud startup error. Each record embeds the EXACT request payload (`messages` verbatim) plus `ts_ms`, `model`, `model_hash` (fingerprint-folded, multi-model attributable), `n_tokens`, `verdict`, `matched_tokens`, `prefill_from` — all using the SAME covered-KV definition as /stats, so a capture and its /stats line must agree by construction. `scripts/replay_trace.py` scores the capture (hit_rate = prefill_from.sum / n_tokens.sum, every served request counted — warming included) and re-sends every record verbatim to a live daemon (`--twice` for a warm second pass, `--report out.json`). Tests: 6 unit (record shape incl. verbatim-JSON embedding, empty-payload omission for synthetic constructs, flush-to-disk ordering, env gating) + 1 e2e (`trace_capture_writes_one_jsonl_record_per_request`: three requests → exactly three well-formed records with correct verdicts, covered-KV semantics, and embedded payloads). Replay smoke on the synthetic engine: capture scored 3 req / 24 tok / 29.2% (identical /stats totals); `--twice` replay pass 2 reuses every persisted prefix (7/8 tokens on the repeated prompt) at sub-millisecond walls, with pass-1/pass-2 daemon stats agreeing with the capture's definition.

**Suspend/resume demo MEASURED (2026-10-03, step 6, `scripts/demo_session.py`, Qwen2.5-7B-Instruct-4bit, real mlx-lm engine, Metal, real daemon HTTP, blobs then deleted):** one ~19.8K-token agent-context request built from real repo file bytes, then SIGTERM both processes, restart from persisted disk state, replay the identical request — in both KV tiers:

| leg | verdict | wall | tokens reused | prefill skipped |
|---|---|---|---|---|
| f16 cold (fresh daemon, empty blobs) | miss | 34.5 s | 0 / 19,847 | — |
| f16 warm (same process) | hit | 1.56 s | 19,846/19,847 | ~32.9 s |
| f16 RESUME (restart from disk) | hit | 1.59 s | 19,846/19,847 | ~32.9 s |
| q8 cold (`MLXCACHE_KV_BITS=8`) | miss | 34.0 s | 0 / 19,847 | — |
| q8 warm (same process) | hit | 1.42 s | 19,846/19,847 | ~32.6 s |
| q8 RESUME (restart from disk) | hit | 1.44 s | 19,846/19,847 | ~32.6 s |

- **Success criterion 1 holds with ~2 orders of magnitude of margin: after a full daemon+sidecar restart the daemon serves the identical request as a HIT in ~1.6 s wall (22x faster than the 34.5 s cold prefill), at 19,846/19,847 tokens reused, in BOTH f16 and q8 tiers.** `lookup_ms` 21–24 covers route + blob load; the remainder of the wall is the 64-token generation the demo requests. Traces record the arc end-to-end: miss → hit → (restart) → hit (matched=19847, prefill_from=19846).
- q8 blob for the same 19,847-token session: 605 MB vs f16 1.07 GB (−43%), consistent with the measured −47% bytes/token ratio; the fingerprint-tied tiers never cross-served (`checkpoints_published` correct in each stack, no quarantine).
- **T22 LANDED (server-side prefix-stable serving): growing MULTI-TURN conversations now reuse across turns with no client or wire change.** Root cause: exact-depth-only lookup under the messages-as-prompt wire contract (measured divergence below). The fix serves an entry whose key diverges from the request at the key's LAST token: the blob holds KV for `key[:-1]`, and KV at position j depends only on tokens `..=j`, so agreement through `len(key)-1` makes every covered position byte-identical (measured on the real Qwen2.5 tokenizer: turn-2's stream (15,663 tok) vs turn-1's entry (7,455 tok): LCP 7,454 = len(key)-1 ⇒ coverage 7,454 instead of 0). Mid-prefix divergence stays unserved (KV past the LCP differs for the diverging request; byte-level cache surgery is unsafe on the q8 g64 tier — documented out of scope). The adapter's trust boundary widened PRECISELY, not loosely: the snapshot check now requires `meta.tokens[:-1] == tokens[:len(meta.tokens)-1]` (exact equality remains the special case); a genuine mismatch still raises CheckpointRejectedError → 422 → quarantine. Stats note: a request SHORTER than the served key's length is never served by the child branch (the adapter rejects prefix_len > len(tokens) as unusable → it would report a hit while running scratch — an accounting lie); such requests miss honestly and scratch. The boundary under-report note below no longer applies; coverage reporting is exact for every served shape. Full-containment behavior is preserved verbatim, and chat-template/token-delta wire modes remain documented alternates, no longer required. The JSON-serialized wire mode IS the stable multi-turn aggregate under T22: only each turn's replaced closing brackets diverge, and the serve rule absorbs exactly that.
