## Problem Statement

Apple Silicon Macs (M5 Ultra Mac Studio: up to 512GB unified memory) are becoming serious local inference engines, but there is no KV cache management layer for MLX/macOS. LMCache (11.9k stars, PyTorch Foundation) does this for vLLM/CUDA only. Every MLX serving process re-prefills expensive shared context — system prompts, repo context, agent histories — because KV state dies with the process. The project: an MLX version of LMCache, as a daemon sitting between coding agents (or any OpenAI-compatible client) and local/network LLM engines.

## What Makes This Cool

- One Mac Studio becomes a shared inference brain: prefill once, every session, every app, every process reuses it. Warm start for a 100K-token repo context in seconds instead of minutes.
- Unified memory removes the wall LMCache exists to fight: no GPU→CPU shuttle, no RDMA. KV persistence avoids a memory-hierarchy shuttle, but it is not free: a 50K-token checkpoint for a mid-size model is plausibly 1-5 GB (bytes/token must be measured — see R1-5 measurement gate below). The daemon's job is still dramatically simpler than LMCache's tiering — policy and persistence, no inter-process tensor shuttling — with the same hit-rate wins.
- Suspend/resume: a 200K-token agent session survives daemon and process restarts.
- The founder is also building a ds4-alternative engine — the daemon's cache contract is designed so their engine is the first-class adapter.

## Constraints

- KV tensors are engine-private (layout, dtype, attention variant). Cross-engine KV sharing is impossible; the contract must be engine-agnostic at the blob/policy level only.
- Cross-machine KV transfer is out of scope for v1 (gigabytes over a network; LMCache needed RDMA for a reason). Multi-Mac arrives later via routing, not KV transfer.
- Solo builder, AI-heavy workflow. Ship value in weeks, not months.
- Sibling product (cache-max) shares the policy DNA: this repo owns the MLX/macOS deep integration (KV persistence, suspend/resume, engine adapters); cache-max owns the universal cross-platform proxy layer.

## Premises

1. Prefill is the dominant cost for coding-agent workloads on Apple Silicon; decode is a hard bandwidth wall. The ds4 evidence: the previously worst-case turns (~20s, full re-prefill after the disk cache evicted the extendable anchor) dropped to 1.6s when fully cached — **12x on fully-cached turns; ~4x on typical warm turns**; the multipliers measure end-to-end turn latency vs the uncached baseline, per the ds4 writeup (adriangalilea.com/deepseek-on-a-mac-studio). Cold-fallback (miss) turns get no improvement over the uncached baseline — which is exactly why eviction policy that protects extendable anchors matters. ## Approaches Considered

### Approach A: Token-Prefix Proxy (minimal viable)
Pure HTTP proxy; hashes token prefixes, routes to the backend holding the longest match, applies ds4-style policy (protect extendable anchors, auto-warm). No KV access in v1. Effort S (weeks), Risk Low. Works with any OpenAI-compatible backend day one; hit-rate ceiling ~60-80% (each engine process still re-prefills what only it has seen). Auto-warm mechanism: issue a prefill-only request so the engine caches the prefix without generating tokens — locally this is `max_tokens: 0`, **which must be verified against mlx-lm's server (folded into the Next Steps #3 benchmark); if rejected, fallback is `max_tokens: 1` + discard the output**; cloud backends generally require max_tokens ≥ 1, so warming is backend-specific policy in the proxy layer. → Evolved into the sibling repo (cache-max).

### Approach B: Cache Contract + Engine Adapter (recommended for this repo)
Approach A plus a formal engine-agnostic cache contract: the daemon indexes token prefixes; engines push/pull serialized KV checkpoints (safetensors blobs keyed by prefix hash) through a small adapter API. Disk tier for suspend/resume included. Founder's engine first-class; mlx-lm adapter second. Effort L, Risk Medium.

### Approach C: Engine-Native Cache
Skip the daemon; build the cache contract into the founder's own engine (OpenAI-compatible API with cache-control endpoints, multi-process cache store via memory-map or XPC). Effort M, Risk Medium. Deferred: orphans the existing MLX community until the engine ships; universality (the 10x vision) delayed.

## Open Questions

- Checkpoint granularity: whole-prefix blobs vs chunked (token-block) blobs — affects partial-hit reuse and dedup. Decide with real traces from cache-max.
- mlx-lm adapter fidelity: in-process cache format vs disk format are lossy across versions — pin per mlx-lm release?
- Eviction policy: ds4's anchor-protection heuristic vs frequency/size-aware — A/B with real traces.
- Does the daemon own the model-loading lifecycle (model manager like llama-swap) or stay cache-only in v1?
- Wired-memory limits: how much unified memory can the daemon claim before it starves engines?

### Contract rules resolved by review (binding, go into the contract spec)

- **Mismatch behavior (R1-1):** on any fingerprint/tokenizer/dtype mismatch, the checkpoint is treated as a miss and the request falls through to normal prefill. Never serve incompatible KV. Mismatched blobs are quarantined, not deleted, for diagnostics.
- **Tokenization ownership (R1-2):** the engine's adapter tokenizes and reports token IDs (it already has the tokenizer); the daemon keys checkpoints by the adapter-reported token-ID prefix and pins the tokenizer artifact hash in checkpoint metadata. The daemon never re-tokenizes.
- **Concurrency (R1-3, refined R2-1):** single-flight on identical uncached prefixes — a concurrent request for the same prefix blocks on the in-flight prefill and is served from its result (one behavior, no either/or); checkpoint blob push/pull is serialized per-blob with an atomic publish (write-temp-then-rename).
- **Restart with in-flight requests (R1-4):** streaming connections drop on daemon restart; clients retry (standard HTTP semantics). Persisted checkpoints survive; in-flight generation state does not.

### Measurement gate before the disk tier is designed (R1-5)

Before committing to checkpoint persistence: measure bytes/token for one representative model (e.g. Qwen3-32B-4bit), measured serialize + deserialize wall time on the target disk, and derive whether the 2s TTFT resume budget holds. If the round-trip fails the budget, v1 ships memory-resident only and the disk tier waits for compression (fp8/quantized KV, CacheGen-style) — the suspend/resume criterion defers with it.

**R1-5 MEASURED (2026-09-25, mlx-lm 0.31.3, Apple Silicon):**

*Qwen2-0.5B-Instruct (24 layers):*
- bytes/token: **12,288** (12 KB/token; 8K tokens = 98 MB)
- serialize: **20 ms**; deserialize: **<1 ms** (memory-mapped safetensors) at 8K tokens; prefill 697 ms

*Qwen2.5-7B-Instruct-4bit (28 layers, 4-bit):*
- bytes/token: **57,344** (57 KB/token; 8K tokens = 459 MB → 50K tokens ≈ 2.9 GB, in the design's 1-5 GB envelope for a mid-size model)
- serialize: **526 ms**; deserialize: **<1 ms** at 8K tokens; prefill **10.2 s**

- **2s TTFT resume budget: HOLDS with margin** at both sizes — deserialize is negligible (memory-mapped); the dominant resume cost is delta prefill compute, not I/O. A hit eliminates the 10.2s prefill.
- **Thesis guard PASSED at both sizes:** generation resumed from a saved-then-loaded prompt cache is token-for-token identical to scratch (`test_roundtrip_logits_identical`, `MLXCACHE_BENCH_REAL=1`). Disk tier viable; suspend/resume NOT deferred.
- **Real daemon end-to-end verified** (7B-4bit): request 1 miss → checkpoint persisted (957 KB, 56 safetensors tensors = 28 layers × K,V) → request 2 hit reuses it. No errors.
- Caveat: 32B-4bit (the named representative) pending; byte/token scales with layer count × hidden size, so expect ~3-4× the 7B figure. Identity + sub-ms deserialize are structural and expected to hold.

## Success Criteria

- **(gated on adapter round-trip benchmark, R1-6)** A coding agent session (e.g. Claude Code pointing at local mlx-lm through the daemon) resumes warm across daemon restart: TTFT for the resumed turn < 2s at 50K+ cached prefix tokens.
- **(gated on adapter round-trip benchmark, R1-6)** Two different processes (agent + chat app) sharing the same model get shared prefix hits: second process's TTFT for the shared prefix < 10% of cold prefill.
- Cross-process + cross-restart hit-rate ≥ 80% of tokens on a real 1-day agent workload trace — assumes adapter-based reuse works (see the "Success-criteria gating" section); if the mlx-lm adapter proves too lossy, v1 target drops to the proxy-layer ceiling (~60-80%) and 80% becomes the stretch goal.
- End-to-end value (the actual goal, premise 5): p95 turn latency and total prefill compute measurably lower than same workload without the daemon (A/B on captured traces, all requests counted including warming traffic).
